# UNM Freedom Confessions

A guest-first mobile app (Expo / React Native, Android first) for its members that replaces the school's Facebook confessions group. Anyone can read the feed; signed-in members post confessions, shoutouts and polls under a unique public nickname, react, comment, vote, and trade in Buy & Sell / Lost & Found. Moderators and admins keep it safe through a keyword hold, a moderation queue, reports and audit-logged identity lookups. Backend is Supabase (Postgres + RLS, RPCs, Realtime, Storage).

## Source of truth

The PRD at `UNM Freedom Confessions V1 PRD.md` (repo root). Read it before starting any module. If code or schema conflicts with the PRD, stop and ask me; do not decide silently.

## Database

`supabase/migrations/*.sql` is the schema. Clients write only through RPCs. Any DB change is a NEW migration file, never an edit to an applied one. Regenerate types after a schema change: `cd mobile && npm run gen:types`.

## Locked decisions

- Guest-first: reading needs no account; posting, commenting, reacting, voting and sharing need sign-in. Guests have no Supabase session (no anonymous sign-ins).
- Posts, comments and listings show the author's nickname. Email is private and visible only to admins, with every lookup audit-logged.
- Nickname is unique and shown on all of the user's posts and comments (old ones too, after a change). The user can change it once every 30 days (`change_nickname`); an admin can rename anyone (`admin_set_nickname`). Names containing flagged words (keywords with the `nickname` scope) are refused.
- Account data: `user_settings` (notification switches, last nickname change) via `get_my_settings` / `set_notification_prefs`; `delete_my_account` (refused for banned or suspended accounts: `account_restricted`) removes the sign-in and private data, closes the person's open listings and keeps the content under a nameless profile, marked for good by `user_flags.deleted_at`. In the app a null author nickname means a deleted account: show "Deleted user" (`lib/authorLabel.ts`), a neutral avatar, no Block action.
- Profile settings: Account (Nickname, About you, My Posts, Notifications, Blocked users, Notification preferences), About (Community rules, Terms, Privacy, Open source notices, Send feedback, Version), Appearance, Log out, then Delete account on its own.
- Open TODOs: Google Play needs a public account-deletion request page; `FEEDBACK_EMAIL` in `mobile/lib/config.ts` is a placeholder. (The retention purge does clear `admin_audit_log`: `20261027140000_purge_admin_audit_log.sql`.) (Done in 7a: `mod_set_user_status` / `admin_set_role` refuse deleted accounts.)
- No real name collected. Email sign-up: password plus a 6-digit email code. Google: native Google Sign-In (`lib/googleSignIn.ts`, ID token to `signInWithIdToken`; never in Expo Go). Terms and 18+ age acceptance is stored in `user_flags.terms_accepted_at`; Google users accept on choose-nickname (`set_nickname(p_nickname, p_accept_terms)`). The session is stored encrypted (`lib/sessionStorage.ts`).
- Feed (Latest) is newest first. Popular is the only engagement-ranked view. Max 3 images per post or listing (none on polls), resized on the phone (1440px long side, quality 0.8) with EXIF removed.
- Post-moderation by default. A keyword match always holds the post for moderator approval. An admin can switch moderation mode to pre-moderation.
- Held content: the author is told that the word filter held it, never which word (`get_my_hold_reason`, `lib/holdReason.ts`).
- Warnings and mutes never name the staff member. The member sees only the reason and the optional note (notification type `warning`, no actor; `get_my_warning`; mobile `lib/warnings.ts`, `WarningSheet`).
- Deleting a chat for me hides it and clears my history only; I can reopen it from the person's profile; reopening never notifies the other member (`reopen_my_chat`, called once when a request answers `already_chatting`).
- Mute = timed suspension (read-only); strikes are information for staff, never automatic punishment (`mod_warn_user`, `mod_mute_user`, `mod_get_strikes`, `member_strikes`; admin panel only, `admin/lib/moderation/warnings.ts`).
- Roles: user, moderator, admin. Moderators and admins manage things in a mobile-friendly Next.js web panel (`admin/`), which requires TOTP. Admins can also look up a user's email (`admin_get_user_identity`), find a user by email (`admin_find_user_by_email`), and delete a banned or suspended account (`admin_delete_account`); each is written to `admin_audit_log`.
- Tabs: Feed, Chats, Create, Buy & Sell (with a Lost & Found toggle), Profile. The Feed has three views under a pinned selector outside the lists, Latest | Popular | Polls (`lib/feedViews.ts`, remembered for the session only, Latest on every cold start; Popular and Polls are mounted only once opened). Announcements, the Get started card and the new-listings banners show under Latest only. Chats is a "coming soon" placeholder: its tab press is prevented and shows a toast; `app/(tabs)/chats.tsx` exists only for deep links.
- Six reactions (Fluent Emoji, license still to be verified), bundled locally. Reactions need sign-in.
- Dark theme = LyriaHub, light = its opposite. App name and logo are editable in the admin panel (`app_settings`).
- Not in V1: DMs, payments, multiple schools, automatic posting to Facebook.
- Push notifications (shipped in V2): the database sends generic-text pushes through Expo, with nothing personal in the message. Each kind can be switched on or off in Profile → Notification preferences (reactions off by default), and permission is asked once after onboarding, with an explainer.
- Staff moderation on the phone (v1.0.2): staff see a Home shield → Moderation hub (`app/moderation/`), the reports and held queues and a staff section in the "…" menu; pure logic in `lib/moderation.ts`, staff check via `useStaff` / `useStaffGuard` (fails closed; every `mod_*` RPC re-checks). Staff push alerts (`staff_report`, `staff_held`) are push-only, hidden from the list and bell, behind the `staff_alerts` switch. Moderators and admins have the same rights here; ban/suspend, profile actions, roles, email/identity tools and audit stay web-only. Privacy rule: no email or auth-identity data ever appears on the phone.
- Onboarding (v1.0.2): the choose-nickname screen (first Google sign-in) explains what is missing on Save and can suggest a name (rules and copy in `lib/chooseNickname.ts`, words in `lib/nicknameSuggestions.ts`); Home shows a "Get started" card (react to 3 confessions) until done or dismissed, stored per user on the phone (rules in `lib/getStarted.ts`, count bumped in `lib/reactionSync.ts`).
- App versions and updates (v1.0.2): members report their app version and platform once per session (`report_app_version` into `member_app_versions`: version, platform, updated_at only; deleted with the account, and `admin_delete_account` also erases push data). The Moderation hub's "Versions in use" shows counts only; "Not reporting yet" means members on builds without the report. Soft popup (`lib/softUpdate.ts`, `SoftUpdatePrompt`): shows when `app_settings.latest_app_version` (default '0.0.0' = off) is newer than the installed version, Update / Later, Later lasts for the session only, waits for the push explainer and sign-in sheet, never over the hard gate or nickname gate. Build type comes from `Updates.channel` (`lib/buildType.ts`: 'production' = Play, everything else = GitHub); Play builds link to `play_update_url`, else `PLAY_FALLBACK_URL`. Hard gate: Play builds never open `update_url`; GitHub builds unchanged; blocking logic untouched. The app and site legal texts must stay word for word identical (`test:legal`).
- Release rules (GitHub to Play): never publish a GitHub APK for 1.0.3 (it would satisfy `min_app_version` without moving people to Play). To migrate: Play 1.0.3 live on the closed-test track and verified by an opted-in tester first, then set `min_app_version` = 1.0.3, `update_url` and `play_update_url` = https://play.google.com/apps/testing/com.unmfreedom.confessions, and an `update_message` telling people to uninstall the GitHub version first (different signing key); announce in the Facebook group a few days before. `min_app_version` stays 1.0.1 until then; never raise it to a version Play does not have yet.
- Q&A and post labels (v1.0.3): a Q&A post is `posts.post_type = 'qa'` on kind 'confession', never a new `post_kind` value (old builds drop unknown kinds). `create_post` must never get an overload (old builds would hit an ambiguous call); `create_qa_post` is separate and both use the internal `_create_post`. `posts.answer_count` counts published top-level comments only (`comment_count` still includes replies). Post numbers are hidden from members but kept in the database and shown to staff (web panel, "#123" search). Members see the kind 'confession' as "Post" (`lib/postKindWord.ts`); the DB value and the app name stay.
- Q&A upvotes (v1.0.3): `comment_upvotes` table, written only through `set_answer_upvote`; upvote only (no downvote); top-level answers on `qa` posts only, never your own answer; answers keep time order. Reactions stay on replies and on all other comments.
- Helpful badge (v1.0.3): earned with the top-voted answer on 3 different Q&A posts. A post counts once it is published, at least 48 hours old and has at least 2 answers; the winning answer is by someone other than the asker, with at least 3 distinct upvoters (not its author, not banned or deleted), ties to the earlier answer. Each post's win is recorded once in `helpful_wins` by `award_badges()` and never taken back; the badge is never revoked.
- Comments sheet (v1.0.3 OTA): the comment icon on a feed card (Latest, Popular and Polls) opens a bottom sheet (`CommentsSheet`) for everyone, guests included; the post body opens `/post/[id]`. The sheet is a root-level overlay, NOT a Modal, so toasts and the reaction picker draw above it. Replies stay collapsed by default ("View N replies"). Drafts are in memory only (`commentDraftStore`, keyed `post:<id>`, shared with the post screen), cleared on logout. The sheet closes on route change and before opening a profile.
- New-listings banners (v1.0.4): Feed tab only, guests too. Markers are local only, one record per account key (user id or `guest`), stored as the server's mark strings verbatim, forward-only (`advanceMarker` = max, serialized writes). The mark is taken before the list load, and a visit commits only after a successful fresh load of the default list (no search, Lost & Found type "All"); clearing runs only when the refreshed count is above 0; the hide-sold/returned toggle does not block clearing. No count call before the session is restored and the membership is known. The 5-second margin in `get_listing_updates` is best-effort.
- Avatar card: shown once, only right after onboarding (sign-up code or first nickname), marked seen the first time it is shown, per phone (`lib/avatarPrompt.ts`, `hooks/useAvatarPrompt.ts`; `markPending` is called from `verify.tsx` and `choose-nickname.tsx` only).

## Engineering rules

- The app runs only in its development build (expo-dev-client); Expo Go can no longer run it. Rebuild (`eas build --profile development`) only when a native dependency or native config (app.json plugins, permissions, icons, splash) changes; JS changes need no rebuild. `android/` and `ios/` are generated by prebuild and never committed.
- OTA updates: `runtimeVersion` policy is `appVersion`. Any change to a native dependency or native config requires bumping `version` in app.json and a new build; JS-only changes can ship as an EAS Update on the matching channel (development, preview, production).
- Anything pinned to the bottom edge (bars, composers, sheets) takes its bottom padding from `useBottomInset()` (max of the safe-area inset and 12) plus its own padding. Buttons and rows use a min height with vertical padding, never a fixed height.
- Branding assets in `mobile/assets/branding/` are generated by `npm run branding` (`scripts/make-branding.mjs`, sharp) from `mobile/public/unmlogo.png`, which stays untracked. Do not edit the generated PNGs by hand.

- Strict TypeScript, no `any`. Use the generated `mobile/types/database.ts` types everywhere.
- Reuse before creating. Small modular files. Comment only non-obvious logic.
- Performance first: cached feed (persisted TanStack Query), skeleton loading, no spinners on filter switches, filter locally, keyset pagination.
- Security first: validate inputs (Zod on the client, the DB re-validates), no secrets in the app, RLS and RPCs are the only write path.
- Exception: supabase/functions/storage-cleanup reads the platform-provided SUPABASE_SERVICE_ROLE_KEY from its runtime environment; the key itself is never in the repo.
- `PersistQueryClientProvider` wraps the whole app, outside any auth gate. Auth bootstrap never blocks rendering.
- DB error codes map to user-facing text only in `mobile/lib/errors.ts`.
- Realtime only through `hooks/usePostgresChanges` (UUID topic per subscription, foreground only, resubscribes on sign-in/out). A payload is a signal to refetch, never rendered directly (it has no nickname).
- Photos only through `lib/photos`: `processPhoto` (1440 px, JPEG 0.8) then `uploadPhoto` (reads bytes with expo-file-system `new File(uri).bytes()`, never `fetch(file://)`; strips EXIF/XMP/IPTC; uploads to `post-images/<uid>/<uuid>.jpg`). Order on submit: validate, upload, then the RPC.
- Gestures that must hold the touch inside a scrolling list (press-and-hold, drag) use react-native-gesture-handler (`GestureHandlerRootView` wraps the app), not PanResponder or View responder props. Per-frame state lives in Reanimated shared values, not React state.
- Dev logging only through `lib/log.ts` (`logError` / `logInfo`, dev only, redacted by `lib/redact.ts`). No direct `console.*` calls; never log secrets, tokens, OTPs or full emails.
- Dev seed data lives in `supabase/seed/` (not migrations); every seed row starts with `[seed] `.

## Admin panel (`admin/`)

- Separate Next.js app (App Router, own `package.json`, not a workspace of mobile): TypeScript strict, Tailwind v4, shadcn/ui (Radix), zod, `@supabase/ssr`. Next 16 uses `proxy.ts` (formerly middleware). Read `admin/node_modules/next/dist/docs/` before using a Next API; versions change.
- Server-only Supabase: no browser client anywhere. Reads and writes go through Server Components, Server Actions and Route Handlers (`lib/supabase/server.ts`). Env vars are `SUPABASE_URL` and `SUPABASE_ANON_KEY` (never `NEXT_PUBLIC_`). The service-role key is never used; `npm test` fails if it is mentioned.
- Cookies are httpOnly, `sameSite=lax`, and `secure` in production (`lib/supabase/cookies.ts`). The session cookie holds only the tokens (`encode: 'tokens-only'`), and the activity cookie holds two timestamps. User fields (factors, email, metadata) come only from `getUser()` (`getValidatedUser()`, cached per request); `aal`/`amr` come from `getClaims()`. Never use `getSession()` or a no-argument `mfa.getAuthenticatorAssuranceLevel()`: both reach the session's `user`, which throws under tokens-only (a source-scan test enforces this). A test keeps a signed-in session's Cookie header under 4 KB.
- Every page and Server Action calls `requireStaff()` or `requireAdmin()` (`lib/auth.ts`): `getUser()` validated by Supabase Auth, `aal2` (TOTP), `is_staff` / `is_admin`. The proxy only refreshes the session, enforces the timeouts and sets the CSP nonce; it is never the only gate. The RPCs check roles again.
- TOTP is mandatory: enrol at `/security/enroll`, enter the code at `/login/verify`. Sessions end after 30 minutes idle and 12 hours in total.
- Server Actions validate input with zod and return `ActionResult` (`{ ok: true, data } | { ok: false, code, message }`). Error codes become text only in `admin/lib/errors.ts`; login errors stay generic.
- Routes and roles live in `lib/access.ts` (the sidebar uses it; a test checks each page calls the matching guard). Every page has loading, error and not-found states, and new sections get no fake data.
- User content (bodies, titles, nicknames) is rendered as plain React text only (never `dangerouslySetInnerHTML`); line breaks via `whitespace-pre-wrap`; keyword highlighting splits the text (`lib/review/highlight.ts`). Images are plain `<img>` with stored width and height from the public `post-images` bucket (`lib/review/content.ts` builds and checks the URLs). Times show in Manila time (`lib/format.ts`); relative times are computed on the server. A null nickname is "Deleted user".
- Server Actions take `unknown`, call `requireStaff()` (or `requireAdmin()` for admin-only tools) as their first statement (a test checks it), validate with zod, and pass ids only to RPCs. After moderation writes call `refreshPanel()` (`lib/moderation/mutations.ts`), which revalidates the whole panel layout (counts, sidebar badges, lists).
- Shared moderation pieces live in `lib/moderation/` (schemas, availability matrix, suspension dates, multi-step report flows, data loaders) and `components/moderation/` (ContentView, dialogs, status badges, history list, URL filters, keyset "Load more"). Reuse them; do not copy a dialog or content view into a page.
- Multi-step actions report partial success honestly and offer a retry for the remaining step only; "already handled" (`not_found` from `mod_resolve_report`, `invalid_transition` on an already-removed item) is not an error.
- Server Components read the clock through `requestNow()` (`lib/request-time.ts`, one value per request), never `Date.now()` directly in render; client components receive `now` as a prop.
- Security headers live in `lib/security-headers.ts` and the CSP in `lib/csp.ts`. `Referrer-Policy` is `same-origin` (header and meta tag), never `no-referrer`: with `no-referrer`, form POSTs send `Origin: null` and Next.js rejects every Server Action. Do not loosen the Server Actions origin check. The CSP uses nonce + `strict-dynamic` for scripts, `'unsafe-inline'` for styles (Radix and the toast library set inline styles). All pages render dynamically (the root layout awaits `connection()`). The panel is never indexed.
- Types: `admin/types/database.ts` and `mobile/types/database.ts` are the same generated file; regenerate both after a migration.
- No `console.*` with credentials, tokens or emails.
